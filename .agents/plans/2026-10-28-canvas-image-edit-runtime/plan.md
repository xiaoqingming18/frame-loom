## 目标

消除表情工具在 Vite 开发模式中的 public loader 导入错误，并修正旧模型档案及不同图片操作的能力判定；不绕过 engine 校验、不扩大用户明确限制。

## 范围与非目标

- 范围：图片检测 Worker 的运行时 URL；contracts 图片编辑能力规则；engine 图片档案、目录更新／兼容和有效档案；画布能力提示及必要回归。
- 基线：`9eda94d`；开始实施时重新检查源码、现有工作区、适用 AGENTS 和目录持久化实现，不依赖诊断时冻结行号。
- 非目标：重做三工具 UI、图像合成算法、全局风格、添加供应商、变更模型默认选择、收费调用、修改真实用户目录／密钥、删除旧任务或初始化标记、扩大 CSP、依赖升级和整个画布审计。
- 证据范围：Vite query 注入链已经本地只读核对；用户实际有效档案尚未取得，旧目录／当前定义缺声明是需要区分的路径。

## 依赖与顺序

- 01 与 02 逻辑独立，顺序推进即可；无需为小型修复增加并行 Agent 和合并成本。03 等两者完成后执行。
- 01 的 URL 单测与 02 的 contracts／目录／画布定向测试归对应子计划，03 不复制其逻辑矩阵；集中执行一次真实开发检查和生产兼容冒烟。
- 实施环境为 Node.js 24.22.x 和锁定 pnpm；构建先完成再启动 E2E，避免并发改写 engine 产物。开始前读取各包实际 scripts，定向测试前按需要构建 contracts。

## 验收

- 01：动态导入收到完整同源 URL；开发不再向 loader 请求 `?import`，生产仍走 `app://frame-loom`，CSP 无新增 Blob／远端许可。
- 02：角度／打光按有效参考输入与适配器边界判定；表情保留专属要求。旧定义缺字段、明确禁用、用户收窄、自定义定义和协议不支持分别有正确结果。
- 02：初始化标记已存在的临时旧目录可升级且可重入；保留配置、约束和历史任务快照；UI 与 engine 接收相同有效能力。
- 03：至少一次真实 Vite 检测响应、一次临时旧目录模型进入 UI／提交的检查、一次生产目录版同源资源及检测兼容冒烟。普通 GET 200、构建成功、手动框选或 mock 均不能替代真实检测。
- 成本边界：不重复 25 情绪预设／像素合成／多图生成矩阵、全仓 E2E、NSIS 安装卸载、跨 GPU、无布局改动的截图矩阵及收费供应商测试。只有失败、后续改动或共享影响扩大才定向重跑／扩测，并记录原因。
- 文档阶段只做 `pnpm run verify`、本次 Markdown 的格式检查与 diff 检查。后续编码阶段的定向测试、类型检查、相关 lint／格式及运行验收均需各自实际结果，不继承此前通过数字。
